Version bumps happen deliberately, inside an OpenSpec change (`CLAUDE.md`): a bump can change
behaviour, add permissions through a library's manifest, or pull in a forbidden SDK. They're never
folded silently into a feature change.

## Where versions live

| What | Where |
| --- | --- |
| Every library and plugin, plus SDK levels and JDK | `src/gradle/libs.versions.toml` (each version pinned exactly; comments record why a version was held back) |
| Gradle | `src/gradle/wrapper/gradle-wrapper.properties` (`distributionUrl`), plus the wrapper scripts and jar |
| SDK platform and build tools CI installs | `.github/workflows/ci.yml` and `release.yml` (`sdkmanager "platforms;android-<n>.<m>" "build-tools;<v>"`) — must match `compileSdk` and `buildTools` in the catalog |
| JDK in CI | `actions/setup-java` `java-version` in the same workflows — must match `jdk` |
| The documented baseline | the Toolchain table in `CONTRIBUTING.md` |

The `app-welcome-screen` design that set the original baseline is archived and read-only; don't edit
it. `CONTRIBUTING.md`'s table is the living record.

## Steps

1. **Find the newest stable release** of each thing being bumped, from its source of truth:
   Google's Maven (`https://dl.google.com/android/maven2/<group path>/group-index.xml` or the AndroidX
   release notes) for AndroidX, AGP and Play services; Maven Central for others; the Gradle releases
   page; Kotlin's GitHub releases. A version containing `alpha`, `beta`, `rc`, `dev`, `eap` or
   `-M<n>` is a pre-release — skip it and say so in the catalog comment, as the existing comments do
   ("1.7.0 is still a release candidate, so 1.6.2 stands").
2. **Check compatibility before editing**:
   - KSP's version must support the Kotlin version (KSP release notes list it).
   - AGP's minimum Gradle version, and AGP's maximum `compileSdk`.
   - The Compose BOM's Compose compiler requirement is the Kotlin version (the Compose compiler ships
     with Kotlin).
   - Room, Navigation and Lifecycle majors against the Compose BOM.
3. **Edit** the catalog, updating the "Newest stable on <date>" comments. For Gradle:
   `./gradlew wrapper --gradle-version <v>` from `src/`, then run it a second time so the wrapper
   scripts and jar are regenerated by the new version. For a new `compileSdk` or build tools, update
   both workflows' `sdkmanager` lines.
4. **Update `CONTRIBUTING.md`'s Toolchain table** to match, row by row.
5. **Verify** — a bump affects everything, so this is the one case that always runs the full suite:
   - `./gradlew test lint assembleDebug` from `src/`.
   - `./gradlew :app:bundleRelease :wear:bundleRelease` (minification and the build permission guard
     on release variants; it needs no signing config to build an unsigned bundle — if it asks for
     one, stop at `assembleRelease`).
   - The full instrumented suite (`emulator-tests` in full mode).
   - The build permission guard passes with no edit to `src/app/manifest-allowlist.txt`. If a bumped
     library adds a permission or a forbidden dependency group (Firebase, ML Kit, datatransport,
     non-wearable Play services), the bump is blocked: hold that library back and record why.
6. **Read the release notes** of every library bumped by a minor or major version for behaviour
   changes, and note any that matter in the change's design.

## Adding a new library

Everything above, plus: `CLAUDE.md` requires a reason that it removes meaningful complexity, named in
the proposal; prefer AndroidX and Kotlin first-party; it goes in the catalog with an exact version
and a comment saying what it's for and which design decision added it; and the README's privacy
section must disclose anything that touches the network (which needs its own accepted proposal).

## Guardrails

- Never use a dynamic or range version (`+`, `latest.release`).
- Never bump versions as a side effect of a feature change; a feature that needs a newer library
  says so in its design and bumps only that library.
- Never edit `manifest-allowlist.txt` to make a bump pass.
