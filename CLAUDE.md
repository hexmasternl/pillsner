# CLAUDE.md

Guidance for AI coding assistants working in the Pillsner repository. Read this before touching anything.

## What Pillsner is

Pillsner is a native Android app, written in Kotlin, that reminds people to take their medication and records whether they did. The name blends *Pills* and *Partner*. The product promise is simple: remind reliably, confirm in one tap, keep the data on the device.

Keep that promise front of mind. When a change makes the app bigger, more connected or less predictable in when it reminds someone, push back or raise it explicitly.

## Current state of the repository

- The project is in early development. The `src` folder is where the Android app lives, and it may be empty or partially scaffolded depending on which change proposals have been applied. Check before assuming a module, package or file exists.
- The `openspec` workflow is fully set up and is the intended way to plan and deliver work.
- The `README.md` describes the product, the intended technology and the repository layout. Keep it in sync when any of those change.

## How work gets done: the OpenSpec workflow

Every non-trivial change follows the spec-driven loop. The slash commands are available in this repository.

1. **Explore** with `/opsx:explore` when the request is vague, when a problem needs investigating, or when requirements need sharpening before anything is proposed. This is a thinking mode, not an implementation mode.
2. **Propose** with `/opsx:propose`. This creates a change under `openspec/changes/` and generates the proposal (what and why), the design (how) and the task list. Read the existing specs in `openspec/specs/` first so the proposal builds on agreed behaviour rather than contradicting it.
3. **Apply** with `/opsx:apply`. Work through the tasks in order, marking each complete as you go. Keep the implementation within the scope of the proposal. If you discover the design is wrong, update the design artifact and say so, rather than quietly diverging.
4. **Archive** with `/opsx:archive` once every task is done and verified. This syncs the delta specs into `openspec/specs/` and moves the change to the archive.

Rules of thumb:

- Small, clearly-scoped fixes (a typo, a one-line bug fix with an obvious cause) may skip the proposal step. Anything that changes behaviour, adds a screen, touches scheduling logic or adds a dependency does not.
- The specs are the contract. When code and spec disagree, either fix the code or propose a spec change. Never leave them silently out of sync.
- Do not create files inside `openspec/` by hand. Let the OpenSpec tooling scaffold them so the structure stays consistent.

## Technology and architecture conventions

These are the intended choices. Deviations must be justified in a change proposal.

**Language and platform**
- Kotlin only. No Java source files.
- Native Android. No cross-platform frameworks, no web views for primary UI.
- Target the current stable Android SDK and support a sensible minimum SDK. Do not lower the minimum SDK to gain a feature without a proposal.

**UI**
- Jetpack Compose with Material 3. No XML layouts for new screens.
- Single-activity app. Screens are composables; navigation is handled by a Compose navigation layer.
- Follow Material accessibility guidance. Reminder confirmation must be usable with large fonts, TalkBack and one hand.

**Architecture**
- MVVM with unidirectional data flow: UI state flows down from a view model, events flow up.
- Clear layering: UI, domain (use cases and models), data (repositories, Room, alarm scheduling). The domain layer has no Android framework dependencies so it stays unit-testable.
- Coroutines and Flow for asynchrony. No RxJava, no callbacks where a suspend function will do.
- Dependency injection through a single, lightweight mechanism agreed in a proposal. Do not mix DI frameworks.

**Persistence**
- Room over SQLite, on-device only.
- Every schema change ships with a migration and a migration test. Never enable destructive migration fallback outside of debug builds.

**Reminders and scheduling**
- Reminders are the core of the product and the most fragile part. Use the platform alarm and notification APIs designed for exact, user-facing alarms. Do not rely on periodic background work for the actual reminder moment.
- Handle device reboot, time zone changes, daylight-saving transitions and the user changing the system clock. Each of these must be covered by a test or a documented manual test case.
- Snooze, skip and confirm must each be recorded as distinct intake outcomes. A skipped dose is not a missed dose.

**Privacy**
- No network access, third-party SDKs, analytics or crash reporting unless an accepted proposal adds them and the README discloses them.
- Never log medication names or dosages at info level or above in release builds.

**Dependencies**
- Prefer AndroidX and Kotlin first-party libraries. Add a third-party library only when it removes meaningful complexity, and name the reason in the proposal.
- Keep dependency versions in a single version catalog.

## Coding style

- Follow the official Kotlin coding conventions and the Android Kotlin style guide. Let the IDE formatter and the project lint configuration settle formatting arguments.
- Name things after the domain, not the framework: a *Medication*, a *Schedule*, a *Dose*, an *Intake*, a *Reminder*. See the glossary below and use the same words in code, specs and UI copy.
- Small files, small functions, no clever tricks. Someone reading a scheduling bug at 2 a.m. should be able to follow the code.
- User-facing strings live in string resources, never inline. Design for translation from the start.
- Write KDoc for public domain types and for anything with non-obvious behaviour, especially around time handling.

## Testing expectations

- Domain and scheduling logic: unit tests, fast, no Android dependencies. Test edge cases around midnight, month boundaries, leap days, daylight-saving changes and time zone moves.
- Room: migration tests for every schema version and DAO tests for non-trivial queries.
- Compose UI: screenshot or semantics-based tests for the main flows (add medication, receive reminder, confirm dose, view today).
- Instrumented tests for alarm scheduling behaviour where the platform must be involved.
- A change is not complete until its tests pass locally. Report failures verbatim rather than paraphrasing them away.

## Build and verification

The Gradle project root is the `src` folder. Run Gradle wrapper tasks from there. The tasks that matter most are the debug assembly, the unit test task, the lint task and the instrumented test task. Run the unit tests and lint before declaring any task in a change done, and run instrumented tests when scheduling, notification or database code changed.

## Domain glossary

Use these terms consistently in code, specs and UI.

| Term | Meaning |
| --- | --- |
| Medication | Something the user takes: name, form, strength, optional notes and stock. |
| Schedule | The rule that says when doses of a medication are due (fixed times, intervals, weekdays, or none for as-needed use). |
| Dose | A single planned intake generated from a schedule, due at a specific moment. |
| Intake | The recorded outcome for a dose: taken, skipped, or missed, with a timestamp. |
| Reminder | The notification that tells the user a dose is due. |
| Snooze | Postponing a reminder for a short, bounded period without recording an outcome yet. |
| Adherence | The proportion of doses that were taken as planned over a period. |
| Refill | The point at which stock is low enough that the user should get more. |

## Things to avoid

- Writing application code outside `src`.
- Editing anything in `openspec/changes/archive/` or hand-editing `openspec/specs/` outside the archive step.
- Committing keystores, signing configuration, API keys or local property files.
- Adding network permissions, third-party SDKs or telemetry without an accepted proposal.
- Replacing exact alarms with inexact background work to simplify things.
- Broad refactors bundled into a feature change. Propose them separately.
- Inventing product behaviour that is not in a spec or proposal. When in doubt, ask or propose.

## Git conventions

- Work on `main` only for trivial fixes; use a short-lived branch per change otherwise, named after the change.
- Write commit messages that describe intent in the imperative mood, with the change name in the body when applicable.
- Commit and push only when asked. Never force-push `main`.
- Keep the working tree clean of build output, IDE metadata and local property files; extend `.gitignore` rather than committing them.
